# Стилист-бот — заметки для работы над проектом

Проект ведётся по документации «Telegram-бот "Стилист" (Claude + Gemini)».
Полный документ у владельца; ключевые решения зафиксированы ниже.

## Роли моделей

- **Gemini** — рантайм-провайдер: анализирует вещи через Gemini API из кода бота.
- **Claude** — инструмент разработки (Claude Code в VS Code), не рантайм-зависимость.
  `anthropic` в requirements закомментирован — ставится только при включении
  Claude-провайдера как резерва (этап 5).

## Команды

```bash
.venv/bin/python -m pytest        # тесты
.venv/bin/python bot.py           # запуск
.venv/bin/python scripts/test_gemini.py   # проверка ключа Gemini из .env
```

## Публичный режим

Бот открыт для всех и работает на ключе пользователя, а не владельца.
`OWNER_USER_ID` и `GOOGLE_API_KEY` необязательны: первый даёт `/stats` и работу
без личного ключа, второй — резервный ключ владельца.

## Инварианты, которые легко сломать

- **Парсер один для всех провайдеров.** Текстовый маркер `===DATA===`, а не нативный
  JSON-mode: у DeepSeek/Kimi/Claude поведение различается. Нативный JSON-mode Gemini —
  опциональное улучшение позже, не замена.
- **Порядок роутеров в `bot.py`.** `analysis.router` последним: он ловит свободный текст.
  Хендлер анализа под `StateFilter(None)`, иначе перехватит ответы FSM-онбординга.
- **Отрицание в вердикте проверяется первым.** «НЕ БРАТЬ» содержит подстроку «брать» —
  см. `normalize_verdict`.
- **`max_concurrent_agents` — контроль стоимости, а не только UI.** `analyze_compare`
  отклоняет запрос свыше лимита до вызовов API.
- **`return_exceptions=True` в `analyze_compare`.** Падение одного провайдера из пары
  не должно ронять сравнение целиком.
- **`belt_cm` дробное (42.5).** В документации схема указывает INT — в коде Float,
  иначе фактические параметры владельца не помещаются.
- **thinking-токены тарифицируются как output.** `GeminiProvider` складывает
  `candidates_token_count + thoughts_token_count`, иначе расход в БД занижен.
  На тривиальном запросе thinking даёт ~275 токенов — при оценке бюджета этапа 3
  считать их, а не только видимый ответ.
- **Модель Gemini подбирается под free tier.** У `gemini-2.5-pro` там квота 0
  (`429 RESOURCE_EXHAUSTED`, `limit: 0`), `gemini-2.5-flash` закрыт для новых
  проектов (`404`). Рабочий выбор — `gemini-3.6-flash`. Что доступно ключу,
  показывает `client.models.list()` с фильтром по `generateContent`.
- **`env_file` в `config.py` — абсолютный путь от `__file__`.** Относительный
  `".env"` резолвится от cwd, и запуск отладчиком из корня workspace ронял
  Settings на трёх `missing`-полях.
- **Промпт передаётся через `system_instruction`,** отдельно от пользовательского
  сообщения. Пользовательский текст в системный промпт не подмешивается.
- **Лидер альбома ждёт двух стабильных проверок,** не одной. При одной между
  закрытием группы и приходом опоздавшего фото оно не находит группу, становится
  новым лидером и уезжает вторым запросом к модели — тест
  `test_late_photo_still_joins_album` ловит именно это.
- **Подпись альбома ищется по всем сообщениям группы.** Она висит на первом
  *отправленном*, а лидером становится первое *доставленное* — Telegram порядок
  не гарантирует.
- **Из `message.photo` берётся максимальный размер** по `width * height`, иначе
  в модель уедет превью 90 px.
- **Кеш провайдеров в `factory` — по паре (провайдер, ключ).** Ключ в кеше —
  `sha256` от api_key, не сам ключ. Кеш только по имени провайдера отдал бы
  чужой клиент другому пользователю, то есть его квоту и его историю запросов;
  `tests/test_public_access.py` держит это.
- **Ключ проверяется до скачивания фото.** Иначе бот тратит трафик на загрузку
  альбома, чтобы затем ответить «нет ключа».
- **Сообщение с ключом удаляется до всех проверок.** Даже не подошедший по
  формату ключ может быть чужим рабочим — сначала удаление, потом валидация.
- **Формат ключа по префиксу не проверяется.** AI Studio выдаёт и `AIza…`,
  и `AQ.…`; отсев только по длине и отсутствию пробелов, годность решает
  `probe_key`.
- **`ENCRYPTION_KEY` завязан на токен бота, когда не задан.** Смена токена без
  явного `ENCRYPTION_KEY` делает сохранённые ключи нечитаемыми.
- **Резервный ключ владельца не утекает другим.** `resolve_api_key` отдаёт
  `settings.google_api_key` только при совпадении с `owner_user_id`.

## Что сделано

Этапы 0–1 роадмапа: конфиг с валидацией, схема БД из раздела 4, CRUD,
`PromptBuilder` (методология + параметры + гардероб + последние вердикты),
`ResponseParser`, `GeminiProvider` (async, vision-готов), `LLMRouter`
(single + compare), онбординг FSM, гардероб, журнал, `/model`.

Этап 3: фото и альбомы. `MediaGroupBuffer` собирает media_group в один запрос,
`handle_photo` скачивает максимальный `PhotoSize`, даунскейлит и отдаёт в vision;
подпись идёт как `input_text`, `input_type` — `photo` или `photo+text`.
Текстовый и фото-путь свели в общий `_analyze_and_reply`. 54 теста.

Замер на реальном вызове: одно фото 1024 px — 1781 входных токенов
(текст промпта + картинка), ответ 2150 с учётом thinking, ~13 с.

Замеры: обхваты вводит пользователь, полуобхват считается (`services/measurements.py`)
и уходит в промпт вторым числом — продавцы указывают замеры вещи по плоскости.
Вишлист: `/wishlist`, кнопка под разбором, блок в промпте.

Публичный режим: `google_api_key_enc` в `users` (Fernet), `services/crypto.py`,
`services/api_keys.py` (`resolve_api_key`, единое сообщение об отсутствии ключа),
`handlers/api_key.py`, `handlers/admin.py` (`/stats` под `IsOwner`), `/forget`.
`OwnerOnlyMiddleware` удалён. 115 тестов.
